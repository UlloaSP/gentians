Executive Summary

GENTIANS implementa un aprendiz de programas ASP por muestreo de reglas, colocacion de variables con clingo, y busqueda genetica sobre combinaciones de reglas. La idea es interesante: usa ASP para podar el espacio sintactico de reglas y otro ASP/clingo para evaluar cobertura de ejemplos.

La implementacion actual valida piezas internas, pero no valida suficientemente producto. El test suite normal pasa porque casi solo cubre utilidades. Los benchmarks oficiales estan rotos por una API antigua. Varios claims de README/CLI no estan soportados end-to-end: #neg en parser, -ua, --comparison lt, --cr, poblaciones pequenas, y context examples en cobertura.

How GENTIANS Works Internally

1. InputBuilt-in example via -e or file via parser. Input contains background ASP, examples, and mode bias.
2. Language Bias#modeh and #modeb become ModeDeclaration. CLI adds aggregates, comparisons, arithmetic.
3. SamplingProgramSampler randomly samples rule stubs with holes _____.
4. Variable PlacementVariablePlacer builds an ASP encoding to assign variables to holes and enforce safety/equality constraints.
5. Rule Validationutils.is_valid_rule rejects unsafe rules, duplicate atoms, invalid comparison/arithmetic variable reuse.
6. Genetic SearchStrategy initializes population, evaluates coverage, does tournament/crossover/mutation.
7. CoverageClingoInterface wraps candidate rules with optional r(i) switches, computes covered positive/negative examples.
8. OutputStops if full positive coverage and zero negative coverage found; otherwise prints current best.

Product Validation

Are we building the product correctly?

Not yet. Current engineering loop does not protect the core product claims.

  • Tests pass but miss critical user-facing flows.
  • Benchmarks are stale and fail before timing.
  • CLI accepts invalid configs instead of validating arguments.
  • Search is nondeterministic and has no seed option, making regressions hard to reproduce.
  • Failure modes print empty programs or tracebacks instead of product-level diagnostics.
  • README claims are broader than validated behavior.

Are we building the correct product?

Maybe, for research users. The concept is coherent if product goal is: learn small ASP programs from examples with bias-driven search and support for selected aggregates/operators. It is not yet correct if product goal is a robust general ASP inductive learner.

Recommended Validation Plan

  1. Fix benchmark harness to current VariablePlacer(args) API and rename file to test_benchmarking.py or configure pytest.
  2. Add parser tests for #pos, #neg, context, whitespace, arity > 9, and malformed input with good errors.
  3. Add CLI smoke tests with deterministic seed: coin, subset_sum, 4queens, file input with neg examples.
  4. Add support matrix tests: one minimal task for each advertised feature: negation, disjunction, aggregate sum/count, comparison lt/neq, arithmetic add/sub, auto bias, invention.
  5. Separate "candidate syntax generation" benchmarks from "end-to-end learning" benchmarks.
  6. Define product acceptance: for each built-in example, expected learned program or expected coverage threshold within time/sample budget.
  7. Add CLI argument validation: pop_size >= tournament_size, aggregate syntax, unsupported flags such as --cr.
  8. Document unsupported ASP features explicitly instead of implying broad ASP support.
